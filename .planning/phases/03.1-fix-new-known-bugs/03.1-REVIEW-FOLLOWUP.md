### CR-03: Повторное чтение отклоняет изменения даты и напоминания

**Исходная классификация:** BLOCKER, P1. **Статус:** fixed в проверенных сценариях.

**Файл:** `D:/myProjects/Android/wellWell/components/Todo/Todo.tsx:66-72`; начальная проверка — строки `55-58`.

**Что исправлено:** при первом чтении обе ветки отклоняют несовместимый `isRepeat` и несовпадение сохранённой даты с датой пропса. Исходный сценарий «старый пропс одноразовой задачи удаляет уже повторяющуюся запись» больше не воспроизводится. Проверены оба направления смены типа и изменение даты до первого чтения.

**Дополнительное исправление:** после `await getTodo(current.id)` условие теперь сравнивает также `latest.nextDate !== current.nextDate` и `latest.reminderDate !== current.reminderDate`. При изменении любого из этих полей вызывается `changedTask()` и выполнение прекращается до `removeTodo`.

**Доказательство:** повторно исполнены реальные `Todo` и storage с mock AsyncStorage. Первое `getItem` запоминает JSON одноразовой задачи, затем моделируется завершение уже начатого редактирования; первое чтение возвращает прежний снимок, второе — свежую запись. Отдельно проверены изменение `nextDate` на `2030-01-01` и изменение `reminderDate` при неизменных типе и notificationId. В обоих случаях assertions подтвердили: **одна запись сохранена без потери новых полей, число записей storage не увеличилось, показан Alert «Задача изменена»**. Маркер: `CR03_SINGLE_DATE_REMINDER_CHANGE_REJECT_PASS`. Прежний результат с удалением больше не воспроизводится.

Это проверка уже прочитанного свежего поля, а не требование глобальной атомарности хранилища: изменение завершилось до второго чтения; одновременно выполняющиеся `setItem` для сценария не нужны. Начатое редактирование может ещё выполняться после закрытия формы по сохраняемому контракту CR-05.

**Ограничение:** окно между последующей проверкой и записью относится к отдельно исключённой общей атомарности. Исправление CR-03 не объявляется общей транзакционной гарантией AsyncStorage.
